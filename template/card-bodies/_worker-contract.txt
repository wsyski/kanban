WORKER CONTRACT — every kanban card on this board, on top of its HARD RULES. This card body is the entire contract: where it differs from your profile's SOUL.md or from the generic kanban lifecycle guidance in your system prompt, the card wins.
- Board access: `kanban_show` if that tool is in your schema, otherwise `hermes kanban --board <BOARD> show <YOUR-CARD-ID>`, and the matching `comment` / `block` / `complete` subcommands for the rest. Never hunt for tools with repeated `tool_search` calls, never search the filesystem for "the board", and never open a board `kanban.db` with sqlite3 — direct reads bypass claim locks and event recording.
- NEVER attach anything yourself, and never paste a file's bytes into a tool. Write your hand-off to the path your card names under `<RUNS>/scratch/<YOUR-CARD-ID>/` and complete the card: the DRIVER attaches every hand-off file it finds there once your card is done. `hermes kanban attach` is refused inside a worker, and the `kanban_attach` tool takes the bytes inline — copying a file through it by hand is how cards are lost. On a lane the plan proves is already satisfied your diff is EMPTY: an empty file is not attached, say `NO CHANGE:` in the result, and never put prose inside a `.diff` file.
- Scope: no branches, no commits, no `request-review`, no filing, decomposing or creating follow-up cards, no design or plan beyond what the card asks, and no subagent or helper dispatch the card does not ask for (large output goes to a file under `<RUNS>/scratch/<YOUR-CARD-ID>/`). Load the skills the card names; do not pull in brainstorming, planning, worktree, branch-finishing or plan-execution skills on your own.
- No one answers in a card session: never ask a question or offer a follow-up, stage what the card says without asking first, and use the `block` the card names only for a missing external decision or a missing tool — never for a test, a plan step or another card's output. Block with `--kind needs_input`, never `block --kind dependency`: the board re-queues a dependency block by itself and counts it as your stop, and waiting on another card is the board's job, not yours. A failing test, a plan step you believe is wrong, or another card's defect is named in your result, and the card completes: the review decides.
- Running anything leaves no cache in the work directory: `work/` holds only what a human receives. Run a Python suite as `PYTHONDONTWRITEBYTECODE=1 python3 -m pytest -p no:cacheprovider …`, and point other tools' caches outside `work/`.
- Your terminal has nobody present to approve a prompt, so the security guard DENIES the command shapes that need a human: a script handed to an interpreter inline (`python3 -c`, `bash -c`, any `-e` flag) and a script piped into an interpreter on stdin. Write the script into `<RUNS>/scratch/<YOUR-CARD-ID>/` with the file tool and run it by its path. A denied command returns `BLOCKED:` and costs you the step: read the reason it gives and change the shape rather than resending it. The same shapes are barred from the commands you write down for a LATER card — a spec recipe, a Run command, a manual check — because that card's terminal is the same: name a script path, `python3 -m …`, pytest or `ls` there.
- GIT IS OPTIONAL — discover it, never assume it. Before your first git command, inside `<WORKDIR>`, run these two, exactly: `git rev-parse --git-dir` and `git check-ignore -q --no-index .` (the `--no-index` is required — without it an entry in the index hides the rule, and the same directory then answers differently from inside it and from the repository root). A repository encloses the directory AND the second command exits non-zero: it is git-controlled, and this card's staging rules apply exactly as the body states them. Any other outcome — no repository, or that command exits zero — it is not git-controlled: stage nothing, put `GIT ABSENT — nothing staged` in your result, and carry on with the card. Never add `-f`, never look for a repository above the work directory, never investigate or explain the absent index: no staged evidence is the expected state there, not a defect, not a finding, and not a reason to end the card. The patch file is required either way: with an index, the body's `git diff --cached -- <your paths>` writes it; without one, write the same file from the worktree, one hunk per file you wrote — `git diff --no-index -- /dev/null <path> >> <RUNS>/scratch/<YOUR-CARD-ID>/patch.diff`, a form that needs no repository at all. Such a patch shows every file whole: it records WHAT you wrote, not how much a revision changed — the driver measures a revision round's change itself, against the version the round was sent. The driver attaches it when the card is done, and a patch that never got written is a finish this rule does not allow.
- The repository's history is not part of your task. Never read `git log`, `git blame`, `git show <commit>:<path>` or any earlier version of a file to explain the work tree's state, and never treat a previous run's artifact as your input: an earlier version of a deliverable is another run's, not yours, and reconstructing it is not evidence about this one. Decide the tree from what is on disk and from the card's own inputs. The one exception is a history command a hard rule in your body names, such as restoring a TW card's test from the patch attached to that card.
- Write the files and the result the card asks for in plain full sentences, not in a terse response style.
- Leave the profile as you found it: write no memories, and create, patch or delete no skills and no config. A backup copy parked under `/opt/backup/agents/` is not a write outside the card's roots.
- End the card exactly as its body says — `complete --result "..."`, or the `block` it names.
