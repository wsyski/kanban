PLAN ACCEPTANCE CHECKLIST — the plan passes when every item holds.
1. Header: Goal, Architecture, Tech Stack, and `Spec: <REFINED>` (or the raw idea's path when planning from it), then a Global Constraints section. No "For agentic workers" line and no execution-handoff section.
2. Coverage: every success criterion SCn in the spec is covered by at least one test step that names it ("covers SC2"), or is marked `manual at Gc` in the spec's Verification recipe. When the spec is the raw idea, its Done-means lines stand in for SCn. Nothing outside the spec's Scope-in; Scope-out items and stated Assumptions are not gaps.
3. Stack: every tool in Tech Stack cites the Findings line that shows it present ("F3"); every Run command is the one the spec's Verification recipe gives.
4. Tasks: each has Files (exact paths under <WORKDIR> or a declared target root), Interfaces, and steps tagged [TW] (the tests the lane's TW card writes and runs — say what the run is expected to PROVE: the FAIL and its message where the work directory is empty, the criterion itself where the behaviour is already there, so PASS is the evidence. The TW card works BESIDE the C card, so that FAIL is a prediction the review re-derives from the two patches, not something a card will observe; only on a lane that runs unit tests), [C] (write the code, run the Run commands) or [TI] (integration tests, only on a lane that runs them; each step names the SEAM it drives — the entry point, command or public interface — and where the deliverable needs something to be reachable end to end, the plan says which [C] step provides it, so the integration card closes a gap the plan anticipated instead of inventing an interface at the end). The TW card's files and the C card's files must be DISJOINT — those two cards write this tree at the same time, so a test never lives inside a file the C card writes, and the C card never needs to touch a test to finish. A [TW] step that demands a FAIL its own Findings contradict fails this item, and so does a test step that asserts a property not achievable with the plan's named toolchain — an output, location or behaviour those tools never produce. Scaffolding and configuration fold into the task that needs them. Every step also says what ticks its plan-file checkbox: the lane's done criterion is that all of them are ticked, and the plan gate releases the TW card BESIDE the C card, so the FAIL a [TW] step predicts is never observed by the card that writes it — a step whose tick no card can honestly make from the evidence the plan names (the review's re-derivation of the patch pair, the run output the step records) fails this item. TICK SENTENCE: write it in one of the two forms a card can make — on a [TW] step, tick on the review card's re-derivation of the predicted FAIL from the two patches; on a [C]/[TI] step, tick on the exact line the recorded command prints. DERIVED VALUE: every expected value a step names — an output, a status, a printed result — is DERIVED in the step itself, as the expression together with the command that evaluates it under the plan's named toolchain and version, or written `UNVERIFIED — executor confirms by: <command>` (item 5). A value asserted rather than derived, where that toolchain produces another, is the same failure as a tick no card can make: the plan review re-derives the expression and rejects the step.
5. Every code step holds the real code — no TBD, no TODO, no "similar to Task N", no undefined names. A fact the spec does not cover is written "UNVERIFIED — executor confirms by: <command>"; that is allowed and is not a placeholder, but never for a Tech Stack tool.
6. Stage-only: no step commits, branches, pushes or stashes, and no step carries card mechanics (attach, complete, card ids).
7. Scratch lives in `<RUNS>/scratch/`. The deliverables are exactly the files the Files blocks name, tests included; nothing else is created under <WORKDIR>, and nothing temporary — no cache, harness or fixture — ever lands there.
8. The plan card produced only the plan, and staged nothing: <PLAN> exists under runs/ and stays UNSTAGED, and `git -C <WORKDIR> diff --cached --name-only` lists no path the plan card wrote — hand-offs are attached to their card, never staged, so that command shows only the lane's own work files. An entry in that list that belongs to another card is not a finding, not something to explain.
